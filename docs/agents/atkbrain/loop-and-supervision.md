# 自循环与御主-从者

<ArchifyEmbed src="/archify/atkbrain-loop.html" title="AtkBrain 自循环：御主-从者" />

这一页讲引擎怎么跑：每轮做什么、什么时候停、三种角色怎么分工、"御主"什么时候被请出来。

## 三种角色

| 角色 | 运行形态 | 职责 |
| --- | --- | --- |
| **从者**（lead） | 一个带工具的 Pi 会话，每轮新建 | 读简报、制定本轮计划、把结果写上攻击图、汇总本轮产出。自己不执行攻击动作（后端按角色拦截） |
| **工人**（roles） | 每轮按需拉起的多个 Pi 会话 | 执行具体工作，工种有 recon（探测）、web-exploit（Web 利用）、privesc（提权）、lateral（横向）等，按赛道还会有 src-hunt、flag-hunt |
| **御主**（supervisor） | 一次性、无工具的 Pi 查询 | 读全局简报，输出下一轮的作战方案。只在特定条件下被调用（见下文） |

代码位置：角色定义与提示词在 `agents/prompts.py`，会话编排（拉起、复用、派发）在 `agents/session.py`。

两个对理解很关键的设定：

- **从者每一轮都是新会话。** `session.py:518` 的 `_acquire_pi` 只换系统提示词、不续接旧对话。上一轮发生了什么，完全靠攻击图和由图生成的简报传递（见[攻击图](/agents/atkbrain/attack-graph)）。
- **工人每轮由从者派发。** 派发哪些工种由 `_fanout_roles`（`session.py:148`）决定：优先用御主方案里点名的角色，没有就用默认集合，再经进程池上限截断。

## 主循环每轮做什么

主循环是 `run_project_loop`（`engine/loop.py:1031`），一个项目同时只有一个循环协程。每一轮按顺序做这些事：

1. **检查停止条件**（详见下文"什么时候停"）：目标已达成、预算耗尽、墙钟到点、图长时间无进展等。
2. **处理人工指令**：如果队列里有人发的指令，立即中止当前执行，把指令并入下一轮。
3. **重建简报**：从攻击图读取当前局面（入口、已获权限、未验证漏洞、开放候选、已失败的路径），加上监控数据与御主方案的绑定约束，生成从者的系统提示词（`supervisor_brief.py`，预算 256K 字符）。
4. **执行一轮**：把指令发给从者会话（`session.py:573` 的 `run_turn`）。从者读简报、写计划、派出工人、等工人跑完、汇总写图。
5. **监督评估**：调用 `LoopSupervisor.evaluate`（`supervise.py:1395`）决定是否请示御主（见下文）。
6. **记账**：更新轮次、进展质量、停滞计数，落盘（进程被杀也能从最近一轮恢复）。
7. **回到第 1 步**，直到触发收口。

## 一轮的终点：三个条件，先到先得

| 条件 | 触发 | 行为 |
| --- | --- | --- |
| 收工短语 | 从者的输出文本里出现收尾用语（`engine/turn_close.py` 定义了 11 个中英短语，如"本轮完成"） | 立即中止该会话——一轮说完成就完成，不等它继续输出 |
| 从者返回 | `run_turn` 正常结束 | 立即中止仍在运行的工人会话，给 15 秒宽限收尾（`turn_close.py:24`） |
| 墙钟 | 一轮超过设定时长（默认 15 分钟） | 强制收口 |

## 什么时候整个任务停止

"任务该不该结束"由一组互相独立的判定函数回答，全部集中在 `engine/hunt_clock.py`（纯函数，便于测试）。每个判定都带有防止误判的附加条件，这些附加条件来自实际运行中出现的误判：

| 判定 | 触发条件 | 防误判设计 |
| --- | --- | --- |
| 目标达成 | getshell / flag 集齐 / SRC 达标 | 每轮开头与回合内多处复查 |
| 墙钟硬停 | 总时长超限（CTF 按遍数递增：40/120/180 分钟，之后每遍 +60；红队 12 小时） | 以"遍"为单位，第一遍给足最短时间 |
| 图空转（方案数） | 连续 6 个御主方案都没有产生新节点、新凭据或新权限 | 只有横向跳板数增加才算"有进展"，原地扫描不加计数 |
| 图空转（时长） | 图签名持续不变且无可做之事 | 默认关闭，显式配置才生效 |
| 入口不可达 | 入口连续探测失败 | 已拿到 shell 时忽略入口故障；单次失败不算死，需连续两次或平台已标记环境关闭 |
| API Key 故障 | 输出疑似"缺 Key"报错 | 只在"没有任何工具调用 + 输出很短"时才认定；未达最短执行时长就重开会话继续 |
| 空回合 | 连续 5 轮"无工具调用且输出少于 20 字" | 未达最短执行时长时清零重建会话，而不是结束任务 |
| 回合卡死 | 回合内长时间无任何事件 | 有命令仍在执行不算卡死（区分"在等结果"和"挂了"） |
| 会话故障 | Pi 进程报致命错误 | 指数退避重开（2 秒起）；连续 5 次失败才熔断 |
| stall 暂停 | 图签名不变且无开放候选 | 交旗会清零；红队要到第三圈扫描之后才允许因此暂停 |

另有**扫描螺旋**机制（`engine/spiral.py` 与 `skills/recon-spiral/SKILL.md`）：把探测范围分成三圈（小：top-100 端口 + 常用字典；中：top-1000 + 中等字典；大：全端口 + 递归枚举），连续 6 个空方案才升一圈。作用是防止 AI 一上来就全端口扫（慢且吵），也防止它永远只扫 top-100。

## 御主：什么时候值得花一次模型调用

御主是一次独立的模型查询，问它"下一轮怎么打"。因为每次问询都花钱，`LoopSupervisor.evaluate`（`supervise.py:1395`）先按顺序检查一串条件，任何一条命中就**不问**：

1. 本轮有人工指令 → 跳过（人工指令优先，不需要御主意见）。
2. 上一轮的方案没有被执行 → 先收紧约束重新下发，不换新方案。
3. 本轮失败属于基础设施故障（网络断、环境挂）→ 跳过——入口挂了不属于"方法失败"，不该因此换打法。
4. 距上次问询失败不到冷却时间 → 跳过。
5. 收集纠偏信号（重复用假凭据、已登录还在枚举登录页、该复核的没复核等）。
6. 是否到了该问的时机：没有方案、或连续多轮无高质量进展、或到达检查周期。刚下过方案且局面仍在推进 → 不问。

问的流程：组装全局简报（图、已覆盖的探测、历史方案、可迁移经验）→ 等御主返回（总墙钟 360 秒）→ **失败就放弃本次问询，从者按自己的思路继续，不阻塞**。成功则进入方案绑定。

## 方案绑定：把方案变成硬约束

御主返回的是自然语言方案。直接把它塞给从者约等于没有约束，所以 `compile_binding`（`advisor_bind.py:1280`）把它编译成三类机器可查的清单：

| 清单 | 含义 | 例子 |
| --- | --- | --- |
| **must** | 本轮必须完成的候选 | 优先验证某个已发现的注入点 |
| **deny** | 本轮禁止做的事 | 已有 shell 且 flag 未齐时，禁止再对入口做目录枚举 |
| **ban** | 被拉黑的具体做法 | 已被证伪的战术、产生过重复的路径 |

编译时按图状态分支补全：有空壳方案、缺字段、与当前局面冲突的部分，由规则直接修正——**图的约束覆盖御主的文字表述**。绑定随简报进入下一轮，并在再下一轮回检执行情况：从者没执行绑定就收紧约束重发，连续 3 轮不执行就作废方案重开探索。

## 人工指令的处理

人在控制台对话框发指令后的完整链路：

1. `POST /api/projects/{id}/steer`（`routes.py`）→ 消息进入队列，标记人工打断，异步中止当前 Pi 会话。
2. 主循环的 2 秒轮询发现打断标记 → 本轮立即作废，计数清零。
3. 下一轮：人工文本并入简报的 steering 区块；**接下来 3 轮内御主方案被压制**（`advisor_hold_turns = 3`），监督器也在这几轮里直接跳过问询。

结果是：人工指令不仅打断当前轮，还在之后的几轮里拥有高于自动方案的优先级，且整个过程不依赖模型"记得有人说过话"。
