# 攻击图（attack graph）

攻击图是 AtkBrain 的核心数据结构：一张存在 SQLite 里的图，记录"到目前为止确认了哪些事实、它们之间有什么关系"。`graph/` 目录负责它：`model.py`（约 500 行）定义数据模型与校验规则，`store.py`（约 3700 行）实现全部读写业务，`hypothesize.py` 从图派生下一步候选。建表语句在 `db.py`。

## 它解决什么问题

AtkBrain 的 AI 执行体（从者和工人，见下一页）是**每轮重新拉起的 Pi 进程**，进程结束对话就没了。这意味着所有已获取的信息必须放在进程之外的持久结构里，下一轮才能接着用。AtkBrain 选的结构是一张图，而不是对话记录，原因有三：

1. **可查询。** "当前有哪些已验证的漏洞、哪些主机被拿下"是对图的查询，不用翻历史消息。
2. **可校验。** 每个节点入库前过一遍规则校验（见下文），模型的夸大表述在这里被拦截，而不是靠提示词约束。
3. **可展示。** 控制台页面的实时网络图就是这张图的直接渲染（前端用 d3-force），人和模型看到同一个局面。

## 数据模型

节点有九种类型，每种表示一类已确认的事实：

| 类型 | 含义 |
| --- | --- |
| `target` | 授权测试的目标主机 |
| `service` | 目标上发现的服务（如 22/tcp ssh） |
| `info` | 一般性探测信息 |
| `danger` | 疑点：可疑但未证实为漏洞 |
| `vuln` | 已有证据支持的漏洞 |
| `credential` | 获得的凭据 |
| `foothold` | 已实际获得的访问权限（shell、后台登录） |
| `honeypot` | 识别出的蜜罐 |
| `goal` | 任务目标达成（getshell / flag 齐全） |

边有五种：`LEADS_TO`（通往）、`EXPLOITS`（利用）、`ESCALATES_TO`（提权）、`PIVOTS_TO`（内网横向）、`CONTAINS`（从属）。每个节点有唯一 key，如 `vuln:443-sqli`，key 的前缀就是它的类型声明。

## 写入路径

模型不能直接改数据库。它调用后端注册的工具写图：`add_node` / `add_edge` 添加普通节点与关系，`report_finding` 上报漏洞发现，`report_shell` 上报拿到的 shell，`report_flag` 上交 flag。**达成类事实有专属工具**：`report_shell` 做的是"确认这个 foothold 真实存在并记录"，不能靠 `add_node` 代替——这保证每种关键事实都有独立的校验逻辑。

所有写入都经过 `graph/model.py` 的校验函数。这些校验针对的是模型输出的常见失真：

| 失真 | 校验行为 |
| --- | --- |
| 标题写"(候选 RCE)" | 候选字样直接删除：未成立的 RCE 不允许出现在标题里 |
| 用低类型节点占位高类型事实 | key 前缀 `vuln:` 的节点按 vuln 处理，类型判定只升不降 |
| 建了 `vuln:` 节点但没有证据 | 带 placeholder 标记的按 `danger`（疑点）处理，不进入漏洞统计 |
| 把"计划 getshell"写成 `goal` 节点 | 拒绝；`goal` 只能由 `report_shell` / `report_flag` 写入 |
| 在 `vuln` 节点上标 rce 冒充战果 | 不计数；只有 `foothold` / `goal` 节点带落地标记才认定 getshell |
| 严重度乱标 | 按漏洞类别设下限（如 RCE 不低于高危），自动纠正 |
| 把蜜罐当普通目标 | 蜜罐节点的风险分被限制上限，不参与主路径规划 |

一条写入还会触发四个自动动作（`store.py` 的 `upsert_node`）：

1. 广播事件，控制台实时刷新；
2. 满足条件（非占位、且是 rce 或高危以上）的 `vuln` 节点自动生成一条 finding 记录；
3. 从该节点派生 Intent（下一节的"下一步候选"）；
4. 补边：模型经常添加节点却忘记添加关系，写入时自动从当前入口补一条 `CONTAINS` 边，漏洞节点优先挂到同主机的 `service` 下，保证图上不出现"目标直连漏洞"这类失真拓扑。

## 读取路径

图有三个读取方：

- **每轮的指令简报。** 下一轮开始前，引擎从图生成简报：当前入口、已有 foothold、未验证漏洞、开放 Intent、已尝试失败的路径。这是每轮重新拉起的 AI 获得全部局面信息的唯一来源。
- **最优路径计算。** `recompute_rce_path` 在图上计算"入口 → 拿下目标"的最优链：排除横向边，按边权转代价取最短路，终点按落地程度排序（`goal` > 已验证 foothold > 已验证漏洞）。没有合格终点时改为高亮风险最高的疑点节点，界面上标注为前沿提示、不是完成进度。计算结果只给相邻边打标记，页面读取时直接用标记还原，避免每次打开页面都重新计算。
- **控制台渲染。** 前端读图并实时更新，读路径带 2 秒缓存。

## Intent：下一步候选及其状态

每轮执行会派生 Intent——"基于当前图，下一步可以尝试什么"的候选，带状态机：`open → active → verified / disproved`，另有 `deferred`（暂缓）。

两条管理规则值得注意：

- **去重靠归一化的 strategy_key**（来源 + 战术，词序归一，`download-lfi` 与 `lfi-download` 视为同一战术），加数据库唯一索引兜底。同一个猜想换写法不会重复出现。
- **复活规则**：终态（verified/disproved）且证据指纹相同的不重插；证据没变时保持原状态；**证据指纹变了就复开**。也就是说，"此路不通"的结论只在证据不变时成立，出现了新证据（如新拿到的凭据），被否证的路径会重新进入候选。

## 去重与纠偏

finding（漏洞记录）入库按四层顺序去重：显式 ID → 同节点最近一条 → 同标题 → CVE 号或利用位置指纹。命中即合并，合并时用 SQL `COALESCE` 只补空字段、不清已有字段，复核状态只允许前进不允许回退。

此外 store.py 有一组 `reopen_*` / `defer_*` 函数，用于撤销不成立的结案。两个例子：单通道返回 4xx 不能否证整个输入面的可达性；对登录页请求超时不构成"认证无法通过"的否证（必须真正送达过认证处理接口）。这类规则来自实际执行中出现的误判，属于规则层对模型和顾问结论的纠偏入口。

## 与会话树的对照

| | pi 的会话树 | AtkBrain 的攻击图 |
| --- | --- | --- |
| 存储 | JSONL 文件（树） | SQLite（节点 / 边 / finding / Intent 表） |
| 写入方 | 运行时 | 模型经工具写入（过校验）+ 规则层 |
| 回答的问题 | 回到哪个节点重新执行 | 当前局面是什么、下一步执行什么 |
| 模型如何获得上一轮信息 | 续接会话 / 恢复树 | 每轮从图重建简报 |
