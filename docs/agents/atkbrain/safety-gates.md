# 执行安全：四道闸与代理链

AtkBrain 允许模型执行系统命令和发送网络请求，因此每个动作在真正执行前都要通过一组确定性检查。这些检查全部是代码（不是提示词约束），按固定顺序求值，任何一道不通过，动作就不会发生。

::: warning 边界说明
本页只描述约束机制的架构（检查什么、按什么顺序、拒绝时返回什么），不包含任何具体攻击手法。该平台本身仅限已获书面授权的环境使用。
:::

## 检查链总览

![检查链总览 流程图](/diagrams/agents-atkbrain-safety-gates-1.png)

一次工具调用（以 `run_cmd` 执行命令为例）依次通过：

1. **命令守卫**（`exec/guard.py`）：命令内容本身的分类检查。
2. **授权范围**（`scope.py` + `scope_pivot.py`）：目标地址是否在授权范围内。
3. **内网可达检查**（`engine/intranet_reach.py`）：是否具备触碰内网的前置条件。
4. **身份门**（`engine/hop_auth_gate.py`）：与"认证能否通过"相关的结论是否有证据支持。
5. 通过后执行，网络类动作强制经过代理链（`proxy/`）。

## 闸一：命令守卫

`Guard.check_command`（`guard.py:757`）按固定顺序检查命令字符串，返回一个决策对象：允许与否、原因、类别。类别有八种：`destructive`（破坏性）、`policy`（策略）、`proxy`（代理）、`honeypot`（蜜罐）、`self_protection`（自保）、`out_of_scope`（越界）、`scope`（范围）、`ok`。检查分组：

| 序 | 分组 | 检查内容 |
| --- | --- | --- |
| 1 | 本机自毁 | 递归删除系统目录、fork 炸弹、格式化磁盘、关机重启等 |
| 2 | 目标侧破坏 | 数据库写操作（DROP/DELETE/UPDATE 等）、写文件型利用、清库改密。非夺旗赛道额外拦截：支付退款类操作、验证码类高频请求、高并发压测工具 |
| 3 | 策略 | 超长字典文件全赛道禁用；CTF 赛道另禁口令破解类工具 |
| 4 | 代理 | 要求走代理的场景下，拦截绕过代理的行为 |
| 5 | 蜜罐 | 蜜罐目录中的产物只允许静态查看，不允许执行 |
| 6 | 目标判定链 | 按顺序判定目标是谁：平台自身端点 → 本机回环 → 攻击机自身 → 本机网段 → 容器网桥 → 邻近题目 → 内网地址 → 公网地址，各自有专门规则 |
| 7 | 网段扫描 | 对"扫描整个网段"类请求单独判定 |

减少误判的处理：URL 只提取主机名部分（让参数里的测试载荷不触发误拦）、跳过命令的数据体部分、对 `sh -c` 递归解析但对 `python -c` 只提取回环地址、裸域名要求是真实域名格式。

被拒绝时，模型收到的不是简单的"失败"，而是：拦截原因 + 类别 + **替代做法建议**（例如访问内网被拒时，提示需要先建立跳板）。这让它被拦后能调整方向，而不是反复尝试同一动作。

## 闸二：授权范围

`scope.py` 提供 43 个无状态判定函数，回答"这个目标地址当前是否被授权"。覆盖的判定包括：

- 攻击机自身与其所在网段（恒为禁止）；
- 本机回环、容器网桥地址；
- **邻近题目**：同一评测父项目下其它子题的入口地址（同一 IP 的不同端口也算）。这条规则优先于普通范围判定，防止并行的多个任务互相影响；
- 授权清单外的内网地址与公网地址；
- 网段扫描请求（`scan_network_forbidden_reason`）。

范围**扩张**有专门的受控通道（`scope_pivot.py` 的 `try_expand_scope`）：只有当模型通过 shell、SSRF、隧道等机制**实际打通**了某个内网主机（有已验证的证据，且证据不只是"探测有响应"），该主机才会被加入授权清单，同时在图上建节点并标记扩张来源。单个已授权 IP 不等于授权它的整个 /24 网段。

## 闸三：内网可达检查

`engine/intranet_reach.py` 解决的问题是：**没有建立跳板能力之前，不允许对内网发起任何操作**。具体机制：

- 每轮开始时从攻击图读取当前是否具备三类前置能力之一：shell（已拿到某台机器的权限）、SSRF（可控的服务端请求）、tunnel（已建隧道）；
- 把结果刷进守卫，内网类目标在没有前置能力时直接拒绝；
- 只有当对内网主机产生了真实的业务面结果时，才把该主机正式纳入范围。

## 闸四：身份门

`engine/hop_auth_gate.py` 管一类特定的结论：**"这个目标的认证打不打得过去"**。模型有一个已知的失效模式：发了一个请求超时了，就断言"认证无法通过"。身份门的规则：

- 没有前置能力时，不允许对认证问题下"否证"结论；
- 要否证，必须证明请求**真正送达过认证处理接口**（有明确的请求方法与请求体），且响应不是登录页外壳或纯粹的超时；
- 送达动作本身有台账文件记录（`.atkbrain_hop_delivery.json`），可复查；
- 口令类工具（如 ssh 尝试）只允许使用守卫下发的凭据清单内的值。

## 代理链

网络类动作执行时强制走代理（`proxy/` 模块）：

| 机制 | 行为 |
| --- | --- |
| 强制条件 | 代理池启用且非 CTF 赛道时，HTTP 请求必须走代理；没有可用出口时直接拒绝执行，不允许回落直连 |
| 第一跳 | 本机 Yakit MITM（通过 MCP 控制），流量可被人在界面看到、留存证据 |
| 出口验真 | 每个下游代理节点启用前实测：经代理的出口 IP 必须不等于本机直连 IP，否则丢弃该节点并冷却 90 秒；运行中每 4 秒复查一次，出口退化为直连就立即更换 |
| 证书 | MITM 根证书从实际拦截的握手流量中现场提取，更换引擎时旧证书作废，避免用错 CA 校验 |
| 泄漏防护 | 拦截不经过代理栈的原始套接字扫描工具（nmap/masscan 类），因为代理对它们无效，会暴露真实出口 |
